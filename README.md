# Адміністрування GPU та моделей

Один сервіс для сервера з кількома GPU: стан карт і їх бронювання, моделі з HuggingFace, запуск моделей на vLLM
і доступ до них для людей та ШІ-агентів. Два входи з однаковими можливостями: **вебсторінка** (для людей,
зручна з телефона) і **MCP** (для агентів: Claude Code, Google Antigravity, OpenAI Codex, OpenCode).
Програми можуть звертатися до моделей через OpenAI-сумісний **`/v1`**.

Версія 1.0.

## Що вміє

| # | Можливість | Коротко |
|---|---|---|
| 1 | Стан GPU | щосекунди: температура, завантаження, потужність, пам'ять, процеси з власниками, моделі з портами |
| 2 | Бронювання карт | «зайняти» (мета, строк — до якого часу), «звільнити»; чуже — лише примусово й із записом у журнал |
| 3 | Моделі HuggingFace | пошук, оцінка «чи влізе в карту», завантаження з чергою й докачуванням, видалення |
| 4 | Запуск на vLLM | на вибраній карті; порт — сам (найменший вільний); кілька моделей на одній карті; перенесення на іншу карту чи порт |
| 5 | Автопідбір параметрів | за замовчуванням — уся вільна пам'ять (до 95 % карти) і максимальний контекст; відомі помилки старту виправляються самі; вдалі параметри запам'ятовуються |
| 6 | Чат | з будь-якою запущеною моделлю; картинки з буфера, файли, PDF (як є / текстом / картинками сторінок) |
| 7 | Доступ агентів | MCP-інструменти, `/v1` за назвою моделі, збережені системні промпти (`модель@промпт`) |
| 8 | Журнал і історія | хто що робив; історія телеметрії (година щосекундно, 30 днів зведено) |
| 9 | Надійність | сервіс systemd; моделі живуть окремо від менеджера й піднімаються після перезавантаження |

## Для людини: вебсторінка

Адреса — `http://<адреса сервера>:<порт>` (порт — `server.port` у конфігу). Угорі оберіть себе («Хто я?»):
без цього сторінка лише показує. Унизу — журнал, «Як користуватися», «Підключити агента (MCP)» і версія.

**GPU.** Картка кожної карти: температура (колір — від порогу, з якого карта сама скидає частоти), завантаження,
потужність, пам'ять, процеси (натисніть — видно команду), моделі з портами. Колір картки: звичайна — вільна;
синя — заброньована; жовта — працює без бронювання (процес чи модель) або строк бронювання минув; червона — немає даних.
Прострочене бронювання само не знімається: його знімає людина.

**Моделі.**
- Пошук на HuggingFace; натисніть на модель — побачите розмір, «чи влізе» й кнопку «Завантажити».
- Один список; галочки «запущені» / «завантажені» вибирають, що показувати.
- Незавершене завантаження показує «помилка завантаження» чи «скасовано» і скільки вже є; «Продовжити завантаження» докачує з місця зупинки.
- «Новий запуск»: карта і частка пам'яті повзунком. «макс» — менеджер сам бере всю вільну пам'ять і найбільший контекст.
- Під кожною запущеною копією — її стан, стан карти, «назва для агентів», «Лог», «Зупинити», а також вибір карти й порту
  з кнопками «Скасувати» / «Змінити» (перезапуск на новому місці; якщо не вдалося — модель повертається назад).

**Чат.** Виберіть запущену модель і пишіть. Ctrl+Enter — надіслати, «Зупинити» — обірвати відповідь,
«Почати розмову» — з чистого аркуша. 📎 — файли, Ctrl+V — картинка з буфера; для PDF є вибір «як є», «текст»
або «зображення». Що з цього прийняти — вирішує модель: відмову видно в чаті як є. Розмова живе, поки відкрита
вкладка браузера; назавжди нічого не зберігається.

## Для ШІ-агента: MCP

Підключення — `http://<адреса сервера>:<порт>/mcp` (транспорт HTTP). Готові команди для кожної системи — на сторінці,
розділ «Підключити агента (MCP)»:

| # | Система | Як підключити |
|---|---|---|
| 1 | Claude Code | `claude mcp add --transport http --scope user gpu-manager http://<адреса>:<порт>/mcp` |
| 2 | Google Antigravity | `~/.gemini/config/mcp_config.json`: `{"mcpServers": {"gpu-manager": {"serverUrl": "http://<адреса>:<порт>/mcp"}}}` |
| 3 | OpenAI Codex | `codex mcp add gpu-manager --url http://<адреса>:<порт>/mcp` |
| 4 | OpenCode | `~/.config/opencode/opencode.json`: `"mcp": {"gpu-manager": {"type": "remote", "url": "http://<адреса>:<порт>/mcp"}}` |

Правила для агента:
- **Спершу — `gpu_guide`**, один раз за сесію: там правила, шляхи й команди копіювання. Сервер сам нагадує про це в інструкціях MCP.
- **`user`** у кожному інструменті, що щось змінює, — логін людини в Ubuntu з `users.allowed`. Не знаєте — спитайте людину й
  запишіть рядок `gpu-manager: my user is <логін>` у свій файл правил (`CLAUDE.md`, `GEMINI.md`, `AGENTS.md`).
- **Чуже бронювання** (`force=true`) і **видалення моделі** — лише з дозволу людини.
- Відповіді — стислий JSON без переносів рядків: кожен символ — ваші токени.

| # | Група | Інструменти |
|---|---|---|
| 1 | Карти | `gpu_status`, `gpu_free`, `gpu_who`, `gpu_reserve`, `gpu_release`, `gpu_history`, `gpu_journal`, `gpu_guide` |
| 2 | HuggingFace | `hf_search`, `hf_model` (розмір, «чи влізе», також для частини карти `fraction`) |
| 3 | Завантаження | `model_download`, `model_downloads`, `model_download_cancel`, `models_local`, `model_delete` |
| 4 | Запуск | `model_start`, `models_running`, `model_logs`, `model_move`, `model_stop` |
| 5 | Використання | `llm_ask`, `prompt_save`, `prompts_list`, `prompt_delete`, `files_inbox` |

**Як запустити модель, щоб вона стартувала.** `model_start(repo, gpu, user)` без інших параметрів: модель бере всю вільну
пам'ять карти (до 0.95 — `vllm.default_fraction`: на 0.99 моделі падали від нестачі пам'яті посеред відповіді) і
максимальний контекст. Менеджер сам виправляє відомі помилки (до 5 спроб): спускає частку пам'яті щаблями 0.92 → 0.9, бере точний контекст, який порадив vLLM (чи межу моделі), зменшує `--max-num-seqs` для
гібридних моделей, вмикає `--enforce-eager` при помилці компіляції. Що змінено — у `auto_changes`. Якщо модель усе ж `failed` — прочитайте
підказку й `model_logs` (можна лише рядки помилок), змініть `fraction`, `max_model_len` чи `extra_args` і запустіть знову.
Вдалі параметри зберігаються в профілі моделі й беруться наступного разу. Щоб поділити карту між моделями — явна
`fraction` (напр. 0.45) для кожної.

**Як користуватися моделлю.**
- Коротке питання від агента: `llm_ask(model, prompt, system_prompt=<назва>)` — повертає лише текст відповіді.
- Програми та інші агенти: OpenAI-сумісний `http://<адреса>:<порт>/v1` (`/v1/models`, `/v1/chat/completions`, потік
  підтримується); `model` — «назва для агентів». `модель@промпт` підставляє збережений системний промпт: довгий промпт
  зберігають один раз (`prompt_save`) і далі передають лише назву.
- Моделі слухають лише `127.0.0.1`; ззовні — тільки через менеджер.

**Файли для моделі — без витрати токенів агента.** Агент кладе файл у свою теку (`files_inbox(user)` дає її шлях і
команди `rsync`; тека — `files.inbox_dir` у конфігу, напр. `/srv/gpu-inbox/<логін>/`) і передає лише шлях:
`llm_ask(model, prompt, files=["/srv/gpu-inbox/<логін>/<задача>/фото.png"])`. Картинки, аудіо й відео модель читає сама
(менеджер запускає її з `--allowed-local-media-path` і з групою теки), текст і PDF (`pdf_mode`: `text` чи `images`)
вставляє в повідомлення менеджер. Програми через `/v1` передають картинку, аудіо чи відео посиланням
`file:///srv/gpu-inbox/<логін>/…` в `image_url` / `audio_url` / `video_url`. Модель, запущена до цієї зміни, читає
файли лише після перезапуску.

**OpenCode з моделлю сервера як основною.** OpenCode працює через виклик інструментів, тож модель має стартувати з
`extra_args=["--enable-auto-tool-choice", "--tool-call-parser", "<парсер>"]` (парсер — з картки моделі на HuggingFace;
зазвичай `qwen3_coder` для нових Qwen, `hermes` для Qwen2.5, `llama3_json` для Llama 3, `openai` для gpt-oss). Далі —
у `~/.config/opencode/opencode.json` (злити з наявним; `<назва>` — «назва для агентів»):

```json
{
  "$schema": "https://opencode.ai/config.json",
  "provider": {
    "gpu-manager": {
      "npm": "@ai-sdk/openai-compatible",
      "name": "gpu-manager",
      "options": { "baseURL": "http://<адреса>:<порт>/v1" },
      "models": { "<назва>": { "name": "<назва>", "limit": { "context": 32768, "output": 8192 } } }
    }
  },
  "model": "gpu-manager/<назва>"
}
```

`limit.context` — контекст, з яким запущено модель. Перевірка: `opencode`, команда `/models` → `gpu-manager/<назва>`.
Той самий блок з уже підставленими адресою, назвою й контекстом — на сторінці: «Підключити агента» → «OpenCode з
моделлю сервера».

## Встановлення (адміністратор)

Потрібно: Ubuntu з драйвером NVIDIA, Python 3.12, systemd, CUDA toolkit з `nvcc` ≥ 12.8 (для збирання ядер FlashInfer у
vLLM; системний старий `nvcc` не підходить). Для доступу з інших машин — приватна мережа (напр. Tailscale).

```bash
git clone <репозиторій> ~/gpu-manager && cd ~/gpu-manager
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
python3 -m venv .venv-vllm && .venv-vllm/bin/pip install -r requirements-vllm.txt   # окремо: інші версії torch
cp config.example.json config.json            # впишіть адреси, імена хоста, логіни, шляхи
cp secrets.example.json secrets.json && chmod 600 secrets.json   # токен HF — лише для gated-моделей
sudo loginctl enable-linger "$USER"           # сервіс живе без входу в систему й після перезавантаження
systemctl --user link "$PWD/deploy/gpu-manager.service" && systemctl --user enable --now gpu-manager
curl http://127.0.0.1:<порт>/healthz          # {"ok":true}
```

`deploy/gpu-manager.service` очікує проєкт у `~/gpu-manager` і спільну теку для файлів агентів `/srv/gpu-inbox/<логін>/`:

```bash
sudo groupadd gpuinbox && sudo usermod -aG gpuinbox <логін>     # кожному користувачу й користувачу сервісу
sudo install -d -m 3775 -g gpuinbox /srv/gpu-inbox
sudo install -d -m 2750 -o <логін> -g gpuinbox /srv/gpu-inbox/<логін>   # для кожного користувача
```

Без спільної теки замініть у юніті рядок `ExecStart` на `ExecStart=%h/gpu-manager/.venv/bin/python -m gpu_manager`.

## Налаштування: `config.json`

Кожне налаштування — `{"value": …, "comment": "…"}`; без коментаря сервер не стартує. Після правки — перезапуск сервісу.

| # | Розділ | Що задає |
|---|---|---|
| 1 | `server` | адреси прослуховування (лише конкретні, `0.0.0.0` заборонено), порт, інші імена хоста, часовий пояс для MCP |
| 2 | `users` | логіни, які можна передавати як `user` |
| 3 | `gpu` | частота опитування, історія, поріг «зайнятої» пам'яті |
| 4 | `vllm` | діапазон портів моделей, шлях до vLLM, `cuda_home`, найбільша частка пам'яті, тайм-аут старту, `max_num_seqs` (32) |
| 5 | `models` | кеш HuggingFace, паралельні завантаження, запас диска, параметри оцінки «чи влізе» |
| 6 | `journal` | скільки записів і днів зберігати |
| 7 | `files` | спільна тека для файлів |
| 8 | `paths` | тека даних (`state.json`, журнал, історія, логи моделей, профілі) |

Дані сервісу — у `data/`: `state.json` (бронювання, завантаження, запущені моделі, промпти), `model_profiles.json`
(вдалі параметри моделей; можна правити руками — читається при кожному старті), `journal.jsonl`, `history.sqlite`,
`servers/<назва>.log`, `downloads/*.log`.

## Безпека

Автентифікації немає свідомо: сервіс для кількох довірених людей у приватній мережі. Тому:
- сервіс слухає лише адреси з `server.hosts`; моделі — лише `127.0.0.1`;
- запити з чужим заголовком `Host` відхиляються (захист від DNS rebinding); POST на `/api/` і `/v1/` — лише JSON, а з
  чужим `Origin` відхиляється (захист від CSRF; без `Origin` — дозволено: так працюють агенти й curl);
- додаткові аргументи vLLM не можуть змінити адресу, порт, частку пам'яті чи відкрити доступ до файлів;
- **не відкривайте порт сервісу в інтернет.**

## Розробка

```bash
.venv/bin/python -m pytest tests -q          # GPU_MANAGER_LIVE=1 — ще й живі тести NVML і HF (лише читання)
.venv/bin/ruff check gpu_manager/ && .venv/bin/pyright --pythonpath .venv/bin/python gpu_manager/
```

Поведінку й інтерфейси описано в `docs/specs/`. Тести пише окремий агент лише за специфікаціями, не бачачи коду:
змінюється поведінка — спершу специфікація, потім тести. Правила для ШІ-агентів, що розробляють проєкт, — у `CLAUDE.md`.
